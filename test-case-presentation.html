Test Case คืออะไร

นิยามและองค์ประกอบพื้นฐาน

Test Case คือ เอกสารที่ระบุ เงื่อนไข และ การกระทำ ที่ต้องทำกับซอฟต์แวร์ เพื่อยืนยันว่าซอฟต์แวร์ยังทำงานได้ตามที่ออกแบบไว้ โดยระบุขั้นตอนการทดสอบ ข้อมูลทดสอบ (Test Data) และผลลัพธ์ที่คาดหวัง (Expected Result) ไว้อย่างชัดเจน

จุดสำคัญที่มักเข้าใจผิด

  • Test Case ไม่ได้เขียนเพื่อพิสูจน์แค่ว่า "ฟังก์ชันใช้งานได้"
  • แต่เขียนเพื่อยืนยันว่าระบบทำงาน "ตรงตาม Requirement และ Condition"
  • ระบบที่ใช้งานได้ดีแต่ผิด Requirement ถือว่า ไม่บรรลุวัตถุประสงค์

Feature / Module: Login Page
Test Objective: ตรวจสอบโหลดหน้า
Pre-condition: เปิดเว็บสถานะปกติ
Test Steps: 1, 2, 3 ลำดับชัดเจน
Test Data: 031192 / 031192
Expected Result: แสดงหน้าเปลี่ยนรหัส
Status: ผ่าน

ทำไมต้องเขียน Test Case

เหตุผลเชิงคุณค่าที่ต้องอธิบายให้ทีมและผู้บริหารเข้าใจ

1

ยืนยันว่าตรง Requirement

ระบบที่ใช้งานได้ดีแต่ไม่ตรงกับความต้องการตั้งต้น ถือว่าไม่บรรลุวัตถุประสงค์ของการพัฒนา

2

เป็นแผนที่นำทางให้ Tester

ผู้ทดสอบทุกคนทดสอบด้วยขั้นตอนและข้อมูลชุดเดียวกัน ผลลัพธ์จึงเทียบกันได้อย่างมีมาตรฐาน

3

ใช้ซ้ำได้ทุกรอบ Regression

เมื่อแก้ไขโค้ดหรือปล่อยเวอร์ชันใหม่ นำ Test Case เดิมมารันซ้ำเพื่อยืนยันว่าไม่พังของเดิม

4

เป็นหลักฐานประกอบส่งมอบ

ใช้อ้างอิงกับลูกค้าและผู้ตรวจสอบว่าระบบผ่านการทดสอบครบตามขอบเขตที่ตกลงไว้

5

ประเมินขอบเขตงานและเวลา

จำนวน Test Case สะท้อนปริมาณงานทดสอบ ใช้คำนวณและวางแผนคนและเวลาได้อย่างเป็นรูปธรรม

6

ลดการพึ่งพาตัวบุคคล

คนใหม่เข้าทีมสามารถทดสอบต่อได้ทันทีโดยไม่ต้องรอการถ่ายทอดด้วยวาจา

Unit Test อยู่ตรงไหนของการทดสอบ

Test Level ทั้ง 4 ระดับ และตำแหน่งของ Unit Test

ระดับ 1

Unit Test

ทดสอบฟังก์ชัน/หน่วยย่อยที่สุด

ผู้รับผิดชอบ: ผู้พัฒนา + ผู้ทดสอบ
ระดับ 2

Integration Test

ทดสอบการเชื่อมต่อระหว่างหน่วย

ผู้รับผิดชอบ: ผู้ทดสอบ
ระดับ 3

System Test

ทดสอบทั้งระบบตาม Requirement

ผู้รับผิดชอบ: ทีมทดสอบ
ระดับ 4

Acceptance Test

ผู้ใช้ยืนยันก่อนขึ้นระบบจริง

ผู้รับผิดชอบ: ผู้ใช้งาน / ลูกค้า

สิ่งที่ต้องจำ

  • ยิ่งเจอข้อผิดพลาดในระดับที่ต่ำ (Unit) ยิ่งแก้ไขได้ถูกและเร็ว — ต้นทุนการแก้บั๊กเพิ่มขึ้นหลายเท่าเมื่อหลุดไปถึง Acceptance หรือ Production
  • Test Case ที่เขียนไว้ในระดับ Unit จะถูกนำกลับมาใช้เป็นฐานของ Regression Test ในทุกระดับถัดไป

หลักการในการเขียน Test Case

ยึดหลัก Verification บนฐานของ Requirement และ Condition

4 เสาหลักการเขียน

อ้างอิง Requirement เป็นตัวตั้ง
ทุกข้อความต้องการต้องมี Test Case อย่างน้อย 1 ข้อรองรับ ไม่มีข้อใดถูกข้าม
ครอบคลุมทุกเงื่อนไข (Condition)
ทั้งกรณีปกติ กรณีผิดพลาด และกรณีขอบเขต ต้องถูกเขียนให้ครบถ้วน
หนึ่ง Test Case ตรวจหนึ่งประเด็น
ถ้าไม่ผ่าน ต้องรู้ทันทีว่าพังที่จุดใด ไม่ควรรวมหลายเรื่องไว้ในข้อเดียว
เขียนให้คนอื่นทำตามได้
ขั้นตอนชัดเจน ข้อมูลทดสอบระบุค่าจริง ผลคาดหวังวัดผลได้ ไม่กำกวม

ระดมความคิดเห็นจากทีม

ควรดึงผู้เกี่ยวข้องหลายบทบาทมาร่วมออกแบบ Test Case เพราะยิ่งมีหลายมุมมอง ยิ่งครอบคลุมทุกกรณีมากขึ้น เช่น SA, Developer, Tester และตัวแทนผู้ใช้งาน

เกณฑ์ตรวจคุณภาพ Test Case

  • • ทำซ้ำได้ (Repeatable): คนละคนรันได้ผลเดียวกัน
  • • ตรวจสอบได้ (Verifiable): ผลคาดหวังชัด ไม่ต้องตีความ
  • • ตามรอยได้ (Traceable): โยงกลับไปยัง Requirement ได้
  • • เป็นอิสระ (Independent): ไม่ผูกกับผลของข้ออื่น รันแยกได้

เริ่มเขียน Test Case ได้จากที่ใดบ้าง

4 แหล่งข้อมูลตั้งต้น เรียงจากที่น่าเชื่อถือที่สุดไปหาน้อยที่สุด

1. Requirement น่าเชื่อถือสูงสุด

เอกสารความต้องการที่ผ่านการวิเคราะห์จาก SA แล้ว หรือรับมาจากลูกค้าโดยตรง

2. Flow / Process เห็นเส้นทางครบ

ผังการทำงานที่ SA วิเคราะห์ไว้ ใช้ไล่เส้นทางการทำงานให้ครบทุกสาขาของเงื่อนไข

3. Planning ของทีม ได้บริบทเพิ่ม

ผลจากการประชุมวางแผนร่วมกัน ช่วยเก็บรายละเอียดที่ไม่ได้เขียนในเอกสาร

4. หน้าจอ UI ทางเลือกสุดท้าย

ใช้เมื่อไม่มี Spec หรือเอกสารให้ดู เพราะงาน SA และผู้ทดสอบทำคาบเกี่ยวกัน

ข้อควรระวัง: การเขียนจากหน้าจอ UI อย่างเดียวมีความเสี่ยง หาก Spec เปลี่ยนจะต้องกลับมาแก้ Test Case ทั้งชุด เสียเวลาซ้ำซ้อน

1.1 วิเคราะห์จำนวน Functionality

แตกระบบเป็นฟังก์ชันย่อย เพื่อรู้ขอบเขตงานทดสอบที่แท้จริง

1
รวบรวมขอบเขตระบบ: ระบุโมดูล/หน้าจอทั้งหมดจาก Requirement เช่น Login, Change Password, Dashboard, Info, Form
2
แตกเป็นฟังก์ชันย่อย: แต่ละหน้าจอมีการกระทำอะไรบ้าง เช่น เปิดหน้า, กรอกข้อมูล, กดยืนยัน, แสดงแจ้งเตือน
3
นับจำนวนและจัดกลุ่ม: รวมจำนวนฟังก์ชันทั้งหมด แล้วจัดกลุ่มตามโมดูลเพื่อกระจายงาน
4
จัดลำดับความสำคัญ: ฟังก์ชันที่กระทบผู้ใช้มากหรือมีความเสี่ยงสูง ต้องทดสอบก่อนและละเอียดกว่า
5
ประเมินจำนวน Test Case: แต่ละฟังก์ชันต้องมีอย่างน้อย 1 กรณีปกติ และ 1 กรณีผิดพลาด
สูตรประเมินเบื้องต้น: จำนวน Test Case โดยประมาณ = จำนวน Functionality × จำนวนเงื่อนไขเฉลี่ยต่อฟังก์ชัน

1.2 ตรวจสอบเงื่อนไขการทดสอบ

แต่ละฟังก์ชันมีเงื่อนไขอะไรบ้างที่ต้องพิสูจน์

คำถาม 5 ข้อที่ต้องตอบให้ได้ทุกกรณี

1. Pre-condition: ก่อนเริ่ม ระบบต้องอยู่ในสถานะใด (เช่น อยู่หน้า Login)
2. Input: ต้องป้อนข้อมูลอะไร ค่าถูก ค่าผิด ค่าขอบเขต
3. Action: ผู้ใช้ทำอะไรบ้าง เรียงลำดับอย่างไร
4. Expected Result: ระบบต้องตอบสนองอย่างไร ข้อความแจ้งเตือนคืออะไร
5. Post-condition: หลังทดสอบ ข้อมูลในระบบเปลี่ยนไปอย่างไร คืนค่าหรือไม่

ประเภทเงื่อนไขที่ต้องมีให้ครบ

  • • กรณีปกติ (Positive): ข้อมูลถูกต้อง ระบบทำงานสำเร็จ
  • • กรณีผิดพลาด (Negative): ข้อมูลผิด ระบบต้องแจ้งเตือนถูกต้อง
  • • กรณีขอบเขต (Boundary): ค่าต่ำสุด สูงสุด และค่าว่าง
  • • กรณีสิทธิ์ (Authorization): แต่ละบทบาทเห็นข้อมูลต่างกัน
ตัวอย่างจาก Change Password:
TC04 ปกติ → รหัสเดิมถูก รหัสใหม่กับยืนยันตรงกัน → เปลี่ยนสำเร็จ
TC05 ผิดพลาด → รหัสใหม่กับยืนยันไม่ตรงกัน → แจ้ง "ไม่ตรงกัน"
TC06 ผิดพลาด → รหัสเดิมไม่ถูกต้อง → แจ้ง "รหัสผ่านเดิมไม่ถูกต้อง"
TC07 ต่อเนื่อง → เข้าสู่ระบบด้วยรหัสใหม่ → เข้าได้สำเร็จ

2.2 วิเคราะห์ผลการทดสอบ

เปลี่ยนตารางผลทดสอบให้เป็นข้อมูลสำหรับตัดสินใจ

อัตราการผ่าน (Pass Rate)
จำนวนที่ผ่าน ÷ จำนวนทั้งหมด × 100 → บอกความสมบูรณ์โดยรวมของรอบทดสอบ
ความครอบคลุม (Coverage)
จำนวน Requirement ที่มี Test Case ÷ ทั้งหมด → ป้องกันการทดสอบไม่ครบขอบเขต
ระดับความรุนแรง (Severity)
จัดกลุ่ม Critical / High / Medium / Low → ตัวชี้ขาดว่าขึ้นระบบได้หรือไม่
ข้อบกพร่องตกค้าง (Open Defects)
จำนวนที่ยังไม่ถูกแก้ไข ณ วันสรุปผล → ใช้ประเมินความเสี่ยงที่เหลืออยู่
100%
อัตราการผ่านของรอบทดสอบตัวอย่าง (10 จาก 10 กรณี)
อ่านตัวเลขอย่างระมัดระวัง:
• ผ่าน 100% อาจแปลว่า Test Case ยังครอบคลุมไม่พอ ไม่ใช่ว่าระบบไม่มีข้อบกพร่อง
• ต้องตรวจ Coverage คู่กับ Pass Rate เสมอ
• บั๊ก Critical 1 ตัว สำคัญกว่า Low 20 ตัว

เกณฑ์ตัดสิน Go live / No go live

ข้อเสนอต่อผู้บริหารต้องมีเกณฑ์รองรับ ไม่ใช่ความรู้สึก

GO LIVE — พร้อมขึ้นระบบจริง
  • รัน Test Case ครบ 100% ตามที่วางแผนไว้
  • ไม่มีข้อบกพร่องระดับ Critical และ High ค้างอยู่
  • อัตราการผ่านเป็นไปตามเกณฑ์ที่ตกลงไว้ใน Test Plan
  • ความครอบคลุมของ Requirement ครบทุกข้อ
  • ข้อบกพร่องที่เหลือระดับ Medium/Low มีแผนแก้ไขชัดเจน
  • มีแผนย้อนกลับ (Rollback Plan) หากเกิดปัญหาหลังขึ้นระบบ
NO GO LIVE — ยังไม่พร้อม
  • ยังมีข้อบกพร่องระดับ Critical หรือ High ที่ยังไม่ถูกแก้
  • รัน Test Case ไม่ครบตามแผน หรือถูกข้ามโดยไม่มีเหตุผล
  • ฟังก์ชันหลักที่ผู้ใช้ต้องใช้ทุกวันยังทำงานไม่ถูกต้อง
  • พบข้อบกพร่องด้านความปลอดภัยหรือความถูกต้องข้อมูล
  • ผลทดสอบไม่ตรงกับ Requirement ในสาระสำคัญ
  • ไม่มีสภาพแวดล้อมหรือข้อมูลพร้อมสำหรับใช้งานจริง
บทบาทของผู้ทดสอบคือ "ให้ข้อมูลและข้อเสนอแนะที่มีหลักฐานรองรับ" ส่วนการตัดสินใจขั้นสุดท้ายเป็นของผู้บริหารโครงการหรือเจ้าของระบบ
